# 공개 정책의 보장 범위 조사 방법

2026-09-19 KST. 이번 작업은 실행 실험과 분리한 탐색적 문서·소스 검토다. 결과를 보기 전 등록한 체계적 문헌고찰이나 대표 표본 조사는 아니다. 앞선 실험이 사용한 자체 정책을 공개 정책의 성능으로 합산하지 않는다.

4개 프로젝트에서 이미지 출처, 읽기 전용 루트 파일시스템, 객체 메타데이터 레이블의 세 정책 계열을 목적 표집한다. Kyverno는 이미지 계열에서 서로 다른 정책 API의 예제를 추가로 구분한다. 총 13개 정책·예제 단위를 검토하며, 배포 가능한 정책, template/module, 기본 제공 check, 문서의 custom-check 예제를 같은 종류의 산출물로 취급하지 않는다. Kubernetes VAP와 PSA는 역할을 비교하는 참조 항목으로 두며 임의로 추가 정책 수에 포함하지 않는다.

프로젝트 revision은 앞선 조사에서 고정한 commit을 유지한다. 각 파일의 출처 URL, SHA-256, 검토 시점, 근거 위치를 기록한다. 정책의 설명, 선언된 입력 단위, 실제 필드 접근, 집행 설정, 연결에 필요한 배포 산출물, 확인한 테스트의 계층을 수동 대조한다. 특정 문자열의 존재 여부만으로 전체 보장 범위를 판정하지 않는다.

분류 기준은 다음과 같다.

- 설명과 소스에서 범위를 확인할 수 있는 경우: `SOURCE_SUPPORTED`. 해당 요청에 실제 적용됐다는 증명은 별개다.
- 제품이 문서로 명시한 조건에 따라 보장이 달라지는 경우: `CONDITIONAL`.
- 문서 표현과 소스의 입력 단위가 달라 범위 설명을 보완해야 하는 경우: `SCOPE_CLARIFICATION_NEEDED`. 실행 가능한 취약점이 확인됐다는 뜻이 아니다.
- 해당 정책의 평가 단위가 컨테이너 유형과 관계없는 경우: `NOT_APPLICABLE`.
- 배포 상태나 실행 증거가 없어서 확정할 수 없는 경우: `UNKNOWN`.

하나의 행에 여러 분류가 함께 적용될 수 있다. 예를 들어 소스는 컨테이너 필드를 다뤄도 집행 모드는 조건부이고, 실제 Admission 적용은 UNKNOWN일 수 있다. 부적합 요청을 허용했다고 제품 결함을 확정하려면 약속한 계약, 지원 버전, 배포 연결과 예외, 실제 평가·집행 및 저장 결과를 함께 입증해야 한다.

이번에는 공식 자료와 테스트 정의를 읽고 보장 근거를 조사한다. 공개 보안 정책의 우회나 권한 획득을 재현하지 않는다. 테스트 파일을 발견한 사실과 테스트를 실행한 사실, 객체 단위 테스트와 실제 subresource 요청 테스트를 구분한다. 후자는 근거를 확인하지 못하면 UNKNOWN으로 남긴다.

초기 표집 후 입력 변환과 API 사실 확인을 위해 보조 소스를 추가하여 총 56개 파일을 고정했다. Polaris 레이블 단위는 처음 선정한 문서의 name 레이블 예제를 유지했다. 추가로 읽은 내장 instance 레이블 check와 fixture는 다른 정책과의 혼동을 방지하기 위한 근거이며 새로운 표본으로 세지 않는다. Kubernetes API v0.35.8 파일도 참조 자료이며 정책 표본으로 세지 않는다. 문헌 조사와 판정은 동일한 한 검토자가 수행했으며 독립 검토자 간 일치도를 측정하지 않았다.
