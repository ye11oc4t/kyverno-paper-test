# 공개 정책의 보장 범위 조사 결과

2026-09-19 KST. Kyverno·Gatekeeper·Kubewarden·Polaris의 공개 정책과 공식 예제 **13개**를 목적 표집해 문서와 구현을 대조했다. 정책 소스와 보조 근거 **56개 파일**을 불변 커밋 및 SHA-256으로 고정했다. 이 수에는 참조용 Kubernetes API 파일도 포함되며, Kubernetes를 다섯 번째 정책 표본으로 세지 않는다. 조사 결과는 **제품 공통 결함을 입증하지 않는다. 대신 정책마다 입력 범위, 요청 조건, 집행 모드, 테스트가 입증하는 범위가 다르다는 점과 구체적인 문서 오류를 확인했다.** “모든 도구가 Ephemeral Container를 놓친다”는 주장은 이번 근거와 맞지 않는다. 반대로 이번 정적 검토가 모든 공개 정책의 안전성을 증명하는 것도 아니다.

표본은 이미지 출처 계열 5개, 읽기 전용 루트 파일시스템 계열 4개, 객체 레이블 계열 4개다. 이들은 동일한 정책 13회 반복이 아니다. Kyverno의 registry 제한과 repository 이름 제한, Gatekeeper의 이미지 일치 조건, Kubewarden의 조합 가능한 필터, Polaris의 registry 금지 예제는 의미가 다르다. 레이블도 존재 여부, 값의 정규식, 키 집합, 객체 이름과의 일치가 서로 다르다. 따라서 탐지율·결함률·제품 순위를 산출하지 않았다. 정책별 출처, 계약, 입력 범위, 집행 모드와 테스트 계층은 [대조표](MATRIX.ko.md), 전체 판정은 [coverage.json](coverage.json)과 [CSV](coverage.csv)에 기록했다. 배포용 YAML, template와 sample Constraint, Wasm module 소스, 내장 check, 문서 예제를 구분했다.

우선 원래 가설에 반하는 근거가 분명하다. Kyverno의 `restrict-image-registries`는 일반·init·ephemeral 컨테이너의 이미지 필드를 명시한다. 공개 Chainsaw 정의에는 Ephemeral Container 추가가 실패해야 한다는 단계도 있다. 다만 이 단계는 명령의 실패 여부를 보므로, 실패가 해당 정책 때문인지까지 독립적으로 식별한 증거는 아니다. Gatekeeper의 `K8sAllowedReposv2`도 세 유형을 검사하고 gator 객체 테스트가 이를 다룬다. Kubewarden의 `trusted-repos-policy`도 세 유형의 이미지를 수집하며 ephemeral 수집 단위 테스트가 있다. 따라서 필드 구현 또는 관련 테스트가 생태계 전반에 없다는 설명은 기각해야 한다. 이번에는 이 테스트들을 실행하지 않았으므로 성공 건수로 집계하지 않았다. [Kyverno 정책](https://github.com/kyverno/policies/blob/2716f4a26a3c27590a1d6d960dee4ce043e4fa4a/best-practices/restrict-image-registries/restrict-image-registries.yaml#L30-L37), [Chainsaw 정의](https://github.com/kyverno/policies/blob/2716f4a26a3c27590a1d6d960dee4ce043e4fa4a/best-practices/restrict-image-registries/.chainsaw-test/chainsaw-test.yaml#L49-L53), [Gatekeeper 평가식](https://github.com/open-policy-agent/gatekeeper-library/blob/22a40962f83268769bcec5dfe55e44b5a85c392a/library/general/allowedreposv2/template.yaml#L34-L49), [Kubewarden 수집 코드](https://github.com/kubewarden/policies/blob/062ce69867746d012276e1120017f1c0c7694e22/policies/trusted-repos-policy/src/validation.rs#L54-L88)

**공개 정책이 검사한다는 사실과 기본 설정이 차단한다는 사실도 다르다.** 표집한 Kyverno ClusterPolicy 세 개는 Audit이며 ValidatingPolicy 예제는 Warn·Audit이다. 해당 Chainsaw 정의는 집행 모드를 Enforce 또는 Deny로 바꾼다. 테스트 설정과 배포 예제 설정을 섞으면 실제로 약속하지 않은 차단을 기대하게 된다. Polaris의 이미지 문서 예제와 읽기 전용 내장 check도 warning이며, 문서는 danger를 webhook 거부 기준으로 설명한다. Gatekeeper는 표본 Constraint에서 action을 생략했지만 제품 문서의 기본값은 deny다. Kubewarden module 소스만으로 배포 mode가 정해지지는 않으며 제품 문서는 protect 기본값과 monitor의 관측 목적을 구분한다. 이처럼 의도된 비차단 모드는 그 자체로 탐지 실패나 제품 결함이 아니다. [Kyverno 모드 설명](https://kyverno.io/docs/policy-types/cluster-policy/validate/), [Polaris 예제](https://github.com/FairwindsOps/polaris/blob/c84bb2ea3674ee7ec044584db8c9cc9e8d17bdd0/docs/customization/custom-checks.md#L14-L35), [Polaris 기본 설정](https://github.com/FairwindsOps/polaris/blob/c84bb2ea3674ee7ec044584db8c9cc9e8d17bdd0/pkg/config/default.yaml#L23-L39), [Polaris 집행 설명](https://github.com/FairwindsOps/polaris/blob/c84bb2ea3674ee7ec044584db8c9cc9e8d17bdd0/docs/admission-controller.md#L10-L17), [Gatekeeper 모드](https://open-policy-agent.github.io/gatekeeper/website/docs/violations/), [Kubewarden 모드](https://docs.kubewarden.io/reference/monitor-mode)

**설명을 보완해야 할 구체적인 항목도 있다.** Kyverno의 `require-ro-rootfs` 설명은 컨테이너 일반을 가리키지만 이 공개 pattern의 명시적 대상은 일반 컨테이너 목록이다. 설명에 유형 범위를 적어야 하며, 그 표현만으로 모든 유형·시점에 대한 보장을 확정할 수 없다. Kubewarden의 `readonly-root-filesystem-psp-policy`는 일반·init 검사 범위를 명시하면서 ephemeral에는 `securityContext`가 없다는 이유를 댄다. 그러나 Kubernetes 1.35.8에 대응하는 API v0.35.8 정의에는 해당 필드가 있다. **문서의 API 전제가 틀렸다는 것은 소스로 확인된 사실**이다. 그 사실만으로 지원 계약 위반, 실제 Admission 누락, 실행 가능한 취약점까지 확인된 것은 아니다. 소스 metadata에 적힌 모듈 버전은 1.0.14이며 이 조사에서는 OCI 바이너리의 일치나 배포 상태를 검사하지 않았다. [Kyverno 설명과 pattern](https://github.com/kyverno/policies/blob/2716f4a26a3c27590a1d6d960dee4ce043e4fa4a/best-practices/require-ro-rootfs/require-ro-rootfs.yaml#L11-L33), [Kubewarden README](https://github.com/kubewarden/policies/blob/062ce69867746d012276e1120017f1c0c7694e22/policies/readonly-root-filesystem-psp-policy/README.md#L9-L21), [고정한 Kubernetes API](https://github.com/kubernetes/api/blob/b65ac350d910ec0067b586c1a7cce7f79fa9bdf5/core/v1/types.go#L5191-L5194)

검사 대상의 구조는 YAML만 읽어서도 잘못 판정할 수 있다. Polaris의 `notReadOnlyRootFilesystem`은 `target: Container`와 `schemaTarget: PodSpec`을 함께 사용한다. 엔진은 일반·init 컨테이너를 각각 선택하고 검사할 PodSpec을 재구성한다. 따라서 check YAML에 `initContainers`가 직접 등장하지 않는다는 이유로 init 검사가 없다고 결론 내리면 틀린다. 반면 이 Container 반복 범위와 기존 실험의 직접 작성한 PodSpec 전체 검사는 같은 평가 단위가 아니다. 기존 자체 규칙의 24개 객체 일치 결과를 공개 Container check의 보장으로 옮길 수 없다. 문서의 세부 옵션도 일반·init을 설명하므로 우선 문서화된 범위 제한으로 해석해야 한다. 이 관찰은 Polaris 전체가 다른 유형을 처리할 수 없다는 뜻이 아니다. [반복 코드](https://github.com/FairwindsOps/polaris/blob/c84bb2ea3674ee7ec044584db8c9cc9e8d17bdd0/pkg/validator/schema.go#L251-L274), [입력 변환](https://github.com/FairwindsOps/polaris/blob/c84bb2ea3674ee7ec044584db8c9cc9e8d17bdd0/pkg/validator/schema.go#L341-L364), [대상 옵션](https://github.com/FairwindsOps/polaris/blob/c84bb2ea3674ee7ec044584db8c9cc9e8d17bdd0/docs/customization/custom-checks.md#L44-L54)

세 컨테이너 유형을 모두 열거했다는 사실만으로도 요청 전체의 보장을 확정할 수 없다. Gatekeeper의 읽기 전용 template에는 필드 접근 외에 요청 연산에 따른 조건과 이미지 예외가 있고, sample Constraint 및 선택된 평가 엔진의 역할도 따로 있다. Kubewarden은 module과 metadata 외에 배포 리소스의 요청 규칙 및 PolicyServer 연결을 필요로 한다. Kyverno도 검사식과 match 조건, 지원 정책 API, 실제 생성된 배포 산출물을 구분해야 한다. 이번 검토는 공개 소스의 범위를 확인한 것이므로, 표본 13개 모두의 **실제 Admission 보장은 UNKNOWN**으로 남겼다. 이는 실패 13건이라는 뜻이 아니다. 기존 자체 정책 실험을 소급 적용하거나 소스에 있는 테스트 정의를 실행 결과로 꾸미지 않았다는 뜻이다. [Gatekeeper template](https://github.com/open-policy-agent/gatekeeper-library/blob/22a40962f83268769bcec5dfe55e44b5a85c392a/library/pod-security-policy/read-only-root-filesystem/template.yaml), [Kubewarden metadata](https://github.com/kubewarden/policies/blob/062ce69867746d012276e1120017f1c0c7694e22/policies/trusted-repos-policy/metadata.yml), [Kyverno 정책 API 설명](https://kyverno.io/docs/policy-types/validating-policy/)

객체 레이블 정책 네 개는 이런 비교의 대조 항목이다. metadata를 검사하는 정책을 ephemeral 필드가 없다고 실패 처리해서는 안 된다. Gatekeeper의 선택한 레이블 Constraint는 Namespace를 대상으로 하고, Polaris 문서 예제는 Controller의 이름과 레이블을 비교한다. 또한 Polaris 문서의 name 레이블 예제와 별도 내장 instance 레이블 check는 같은 정책으로 합치지 않았다. Kubernetes VAP는 정책과 binding을 연결하는 실행 기제여서 이 네 프로젝트의 공개 규칙 표본처럼 하나의 내장 보안 정책으로 세지 않았다. PSA가 사용하는 Pod Security Standards도 임의의 사용자 규칙을 대신하지 않는다. 공식 PSP–PSS 대응표는 읽기 전용 루트 파일시스템에 대해 요구사항이 없다고 명시하므로, 그 항목을 검사하지 않는 것을 PSA 결함으로 채점할 수 없다. [VAP 설명](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/), [PSP–PSS 대응표](https://kubernetes.io/docs/reference/access-authn-authz/psp-to-pod-security-standards/)

이 조사로 뒷받침할 수 있는 원인 설명은 **보장에 필요한 조건이 여러 산출물에 나뉘어 있다는 것**이다. 정책 제목은 보안 목적을 설명하지만 실제 계약은 입력 단위, 대상 유형, 요청 조건, 설정과 예외, 집행 행동, 검증 근거를 함께 읽어야 드러난다. 이 연결을 생략하면 관측용 정책을 차단 장치로 믿거나 제한된 대상의 검사 결과를 전체 워크로드 보장으로 오해할 수 있다. 그런 오해가 운영 판단에 쓰이면 규정 준수 보고와 배포 승인에서 보장 범위를 과대평가할 수 있다. 이는 관찰된 소스 차이로부터의 방어적 위험 해석이며 실제 침해의 관측이 아니다. 특정 설계가 왜 도입됐는지, API 변화에 대한 유지보수가 언제 지연됐는지는 변경 이력과 유지관리자 판단을 조사하지 않았으므로 원인으로 확정하지 않는다.

보완은 정책별로 이 계약을 명시하는 데서 시작해야 한다. 컨테이너 유형과 객체·요청 단위, 지원 버전, 배포에 필요한 산출물, 기본 집행 모드, 예외와 검증 수준을 함께 제공하고, 오래된 API 설명은 정정해야 한다. 테스트는 입력 추출 단위 시험, 정책 객체 평가, 실제 적용 경로의 관측을 구별해 표시해야 한다. 특히 파일명이 e2e라는 이유만으로 요청 경로 증거로 세면 안 된다. 수집한 Kubewarden 읽기 전용 정책의 e2e 파일은 dummy이고, 다른 표본의 e2e.bats는 kwctl 로컬 평가다. 배포자는 설치된 엔진의 능력, 선택한 공개 정책의 범위, 자신의 배포 설정을 각각 확인할 필요가 있다. **논문의 현재 주장은 “공통 엔진 결함의 발견”이 아니라 “공개 정책의 보장 범위를 구성요소별로 대조했을 때 드러나는 차이와 문서 정확성 문제”가 적절하다.** 기존 무해한 자체 정책 실험은 엔진이 명시된 조건에서 일관되게 동작한 증거로 별도 유지한다.

이것은 4개 프로젝트·3개 계열의 단일 검토자 탐색 조사다. 저장소 전체 정책, 전체 테스트, 모든 버전 또는 배포 구성을 전수 조사하지 않았다. 태그·소스 metadata 버전은 바이너리 검증을 대신하지 않는다. 불변 링크를 쓴 소스와 달리 보조 온라인 제품 문서는 2026-09-19에 확인한 가변 문서다. [방법](METHOD.ko.md), [출처 잠금 목록](source-lock.json), [무결성 확인](integrity.json)에 범위를 남겼다. 공개 보안 정책에 대한 새 실행 실험은 수행하지 않았다.
