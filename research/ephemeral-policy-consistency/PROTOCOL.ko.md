# Kubernetes Ephemeral Container Admission 정책 적용 일관성 평가

설계 v0.1 · 2026-09-19 · 예정 실행 호스트: KSYBOB · 상태: 본실험 미실행

## 연구 대상과 논리

본래 연구 대상은 일반 컨테이너의 생성과 Ephemeral Container 추가 사이에서 Admission 정책이 일관되게 적용되는가이다. SA 자동 마운트는 대상이 아니다. 사용자 제공 SA 논문에서는 설정상의 관계와 실제 성립 조건을 분리하고 독립 증거로 비교하는 논리만 참고한다.

연구의 출발점은 “배포 시 적용한 정책이 운영 중 추가되는 컨테이너에도 적용되는가?”이다. Kubernetes는 Ephemeral Container를 별도의 subresource로 다루며, Admission 적용 여부에는 요청의 종류와 매칭 조건이 관여한다. 따라서 정책이 존재한다는 사실과 특정 요청에서 정책이 실제 선택·평가·집행되었다는 사실을 구분해야 한다. [Ephemeral Containers](https://kubernetes.io/docs/concepts/workloads/pods/ephemeral-containers/), [Dynamic Admission Control](https://kubernetes.io/docs/reference/access-authn-authz/extensible-admission-controllers/)

논리전개는 정책의 보장 범위 정의, 일반·Ephemeral 컨테이너의 대응 사례 구성, 적용 단계별 증거 비교, 차이의 원인 분석, 방어적 보완과 회귀 검증의 순서다. “모든 도구가 놓친다”는 결론을 전제하지 않는다. 결과가 모두 일치하면 그 결과를 그대로 보고한다.

## 기존 결과의 위치

기존 `experiments/policy-baseline`은 일반 Pod의 직접 작성한 세 정책을 CLI로 평가한 예비 실험이다. 12개 고유 사례를 3회 반복한 결과이며, Ephemeral Container 요청, 실제 Admission 또는 런타임을 비교하지 않았다. 따라서 본실험의 경로 간 일관성이나 보안 결함의 증거로 합산하지 않는다.

이 설계는 앞선 원격 작업에서 제안되었던 권한 획득 여부까지 확인하는 실험보다 범위가 좁다. 무해한 정책 적합성 평가로 요청 처리와 판정의 일관성을 확인한다. 이 결과만으로 권한 상승, 실제 침해 또는 위험 능력 획득을 주장하지 않는다.

## 질문과 반증 조건

RQ1: 두 컨테이너 유형에 적용한다고 명시한 같은 정책 의도가 각 요청에서 기대대로 평가되는가?

RQ2: 차이가 있다면 요청 도달, 정책 선택, 객체 해석, 규칙 평가, 집행 모드, API 반영 중 어느 단계의 증거로 설명할 수 있는가?

RQ3: 공식 정책·예제의 문서상 범위와 구성상 범위가 일치하는가? 도구의 기능 한계와 개별 정책의 범위를 구분할 수 있는가?

RQ4: 확인된 원인에 대한 방어적 보완 후 대응 사례의 정확성과 적용 범위가 유지되는가?

두 프로젝트 이상에서 같은 원인을 입증했을 때만 “평가한 프로젝트들에서 관측한 공통 원인”이라고 쓴다. 의도적으로 좁게 작성한 자체 정책의 실패를 제품 결함으로 세지 않는다. 차이가 문서화된 적용 범위로 설명되면 지원 범위 차이로 보고한다. 모든 대상이 계약을 지키면 공통 결함 가설은 지지되지 않은 것이다.

## 비교 대상과 공정한 비교

| 대상 | 1차 역할 | 상태 |
| --- | --- | --- |
| Kyverno | 무해한 동일 정책 의도의 평가·집행 비교 | CLI v1.19.1만 예비 실험에서 사용; Admission 환경 미구성 |
| OPA Gatekeeper | 같은 정책 의도의 독립 구현 비교 | v3.23.1 릴리스 후보 확인; 미설치 |
| ValidatingAdmissionPolicy | API 서버 내부 정책 평가 비교 | Kubernetes 버전과 함께 고정 예정 |
| Pod Security Admission | 표준 보안 정책의 문서상 적용 범위 대조 | 임의의 명명·이미지 식별 규칙 점수에는 포함하지 않음 |

Gatekeeper와 Kyverno 후보 릴리스는 2026-09-18 공식 GitHub release API에서 확인했다. 후보 버전은 호환성 검증 완료를 뜻하지 않는다. 실행 전 Kubernetes, 런타임, 도구 바이너리, 정책 소스, 바인딩·제약, 예외, 집행 모드와 관련 설정의 불변 버전·해시를 기록한다. VAP와 외부 webhook은 관측 방식이 다르므로 webhook 로그 유무를 동일한 기준으로 요구하지 않는다. [VAP 문서](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/)

공식 정책·예제의 범위 조사는 제품별로 별도 표에 기록한다. 출처와 적용 대상, 평가 단계가 맞는 것만 비교하고, 작성자가 새로 만든 규칙을 기본 제공 정책이라고 소개하지 않는다. PSA는 사용자 정의 규칙의 일반 엔진과 역할이 다르므로 전체 도구 순위에 억지로 합치지 않는다. [Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/)

## 파일럿의 입력과 기대값

파일럿은 정상 권한의 시험용 컨테이너에 적용하는 두 가지 무해한 규칙으로 구성한다. 첫째는 컨테이너 이름이 사전에 정한 연구용 명명 규칙을 만족하는지, 둘째는 이미지 식별자가 사전에 정한 시험용 허용 집합에 속하는지다. 허용·비허용 이미지 식별자 모두 동일하게 무해한 시험 내용만 가리키게 하며, 이미지 내용을 보안 위험의 대리변수로 사용하지 않는다. 실제 식별자와 digest는 입력 동결 시 기록한다.

각 규칙의 의도는 두 컨테이너 유형에 동일하게 적용하도록 선언한다. 적합·부적합 기대값은 이름 또는 식별자의 규범 비교로 작성하며, 엔진별 정책 코드를 정답 생성기로 사용하지 않는다. 이 규칙으로 확인할 수 있는 것은 일반적인 정책 적용과 결과 일관성이다. 특정 securityContext 규칙이나 모든 보안 정책이 같은 결과를 낸다고 일반화하지 않는다.

| 차원 | 값 |
| --- | --- |
| 규칙 | 명명 규칙, 시험 이미지 식별자 허용 집합 |
| 컨테이너 추가 시점 | 일반 컨테이너를 포함한 Pod 생성, 정상 Pod에 Ephemeral Container 추가 |
| 입력의 규칙 적합성 | 적합, 부적합 |
| 초기 정책 엔진 | Kyverno, Gatekeeper, VAP |

2개 규칙 × 2개 경로 × 2개 적합성 = 엔진당 8개 논리 사례이며, 3개 엔진이 모두 평가 가능하면 24개다. 기능 반복을 3회 수행하면 최대 72회 실행이지만 고유 사례 수는 늘어나지 않는다. 지원되지 않거나 유효하지 않은 조합은 별도 표시하고 성공으로 채우지 않는다. 규칙이 적합 입력까지 전부 막는 경우도 실패이므로 차단률 하나만으로 평가하지 않는다.

이 쌍은 완전히 동일한 객체의 API 경로만 바꾸는 실험이 아니다. 컨테이너 유형과 객체 구조도 달라진다. 따라서 차이를 “경로 하나의 인과 효과”로 단정하지 않고 단계별 증거와 통제된 비교로 원인을 좁힌다. 서로 다른 유형에 존재하지 않는 필드를 대응시키지 않는다.

## 독립 증거와 단계별 판정

| 단계 | 확인할 사실 | 해석상 주의 |
| --- | --- | --- |
| 요청 | 올바른 종류·대상·시점의 요청이 처리되었는가 | 클라이언트 출력만으로 판단하지 않음 |
| 적용 | 대상 정책이 이 요청에 선택되었는가 | API 감사 기록만으로 개별 정책 실행을 확정하지 않음 |
| 평가 | 실제 적용된 입력에서 어떤 판정이 나왔는가 | 로그 부재는 미평가의 확정 증거가 아님 |
| 집행 | 판정이 허용·거부·감사 중 어떤 행동으로 연결되었는가 | Audit과 Enforce를 혼동하지 않음 |
| 반영 | 대응 객체에 시험 입력이 저장되었는가 | 성공 HTTP 응답만으로 최종 상태를 단정하지 않음 |
| 실행 | 무해한 시험 컨테이너가 시작되었는가 | 미시작·미관측을 정책 차단으로 처리하지 않음 |

요청·정책 평가 기록·객체 관측은 식별자와 시점으로 연결한다. 저장 상태는 가능하면 읽기 전용 관측에서 확인한다. 데이터 수집 여부도 결과에 포함한다. 정책 코드와 독립된 관측이라는 점과 별도 검토자에 의한 검증이라는 점은 다르므로, 같은 작성자만 검토했다면 이를 명시한다.

결과는 각 단계에 대해 YES, NO, UNKNOWN, NOT_APPLICABLE을 기록하고 실행 오류를 별도로 둔다. 정상 기능 사례가 먼저 성공해야 대응하는 부적합 사례를 해석한다. RBAC 거부, 스키마 거부, 다른 정책의 거부, 이미지 준비 실패를 대상 정책의 올바른 집행으로 세지 않는다.

## 교란요인과 원인 분석

하나의 엔진을 평가할 때 다른 엔진의 차단이 결과를 대신하지 않도록 독립 시험 환경을 사용하고, 유지되는 기본 보안 통제는 기록한다. 운영 클러스터는 평가 대상으로 삼지 않는다. 각 사례는 이력이 섞이지 않는 새 시험 객체로 구성하고, 반복 순서는 기록한다. 객체 UID, 정책 revision, Kubernetes 버전이 다른 기록은 같은 사례의 연속 증거로 합치지 않는다.

관련 설정이 충분한지 확인하지 않고 특정 제품의 판정 오류를 선언하지 않는다. 원인 후보는 요청 적용 범위, 컨테이너 유형별 필드 해석, 실제 규칙, 예외·바인딩, 집행 모드, 관측 불충분으로 나눈다. 확인된 차이에 한해 해당 원인을 방어적으로 보완하고 다른 요소는 고정하여 비교한다. 일부러 보안 설정을 약화한 대조군은 사용하지 않는다.

공식 규칙에 관한 결론은 해당 규칙의 불변 소스와 문서상 계약으로 뒷받침한다. 무해한 자체 규칙의 결과를 공식 보안 규칙의 결함으로 옮겨 쓰지 않는다. 보완 내용을 고정한 후 별도로 검토한 추가 무해 사례로 회귀를 확인한다. 결과를 본 후 기대값을 바꾸면 새 실험 revision으로 분리한다.

## 지표와 논문의 주장 범위

주 지표는 각 경로에서 규범 기대값과 일치한 비율, 두 경로 모두 기대대로 평가된 대응쌍 비율, 평가 가능한 사례의 비율이다. 단순히 두 경로의 결과가 같다고 성공으로 세지 않는다. 둘 다 부적합 입력을 허용하거나 둘 다 적합 입력을 거부할 수도 있기 때문이다.

오거부는 유효한 적합 입력을 대상 정책이 거부한 경우, 누락은 적용 대상인 부적합 입력을 해당 계약상 허용한 경우로 정의한다. 원인을 확인하지 못한 결과는 미분류로 둔다. UNKNOWN, 오류, 제외 수를 전체 계획 사례 수와 함께 공개한다. 반복 실행을 독립 표본으로 취급하거나 작은 목적 표집으로 생태계 전체의 결함률을 추정하지 않는다.

이 연구에서 관측되는 일관성 공백은 정책 보장을 신뢰하는 배포·운영 판단에 영향을 줄 수 있다. 그러나 명명·이미지 식별 규칙의 불일치만으로 실제 보안 침해를 입증할 수는 없다. 특정 위험 설정과 권한 획득에 대한 주장은 이 파일럿의 범위 밖이다. 결과는 정책 적용 범위와 회귀 검증의 개선 근거로 사용한다.

논문은 “정책 존재와 실제 적용의 구분 → 대응 사례 및 독립 기준 → 단계별 일관성 평가 → 확인된 원인 → 방어적 보완 및 검증” 순서로 전개한다. 공통 원인이 관측되면 평가한 버전과 정책 범위에 한정해 설명하고, 모두 일치하면 그 결과와 지원 전제를 보고한다. 특정 Kyverno PR은 원인이 확인된 경우의 구현 산출물이며 연구 전체의 결론을 대신하지 않는다.

## 현재 완료 범위

이번 변경은 연구 주제와 평가 설계를 바로잡은 문서 변경이다. 새 Admission 실험, 도구 설치, 클러스터 생성 또는 정책 배포는 수행하지 않았다. 실행 전에는 시험 환경과 정책 소스·의도·입력·증거 수집 방법을 고정해야 한다. 성능 비교, 다른 subresource, 다른 보안 목표는 본 파일럿의 결과와 별도 필요성이 확인되기 전까지 추가하지 않는다.
