# 수정 내역

기존 판정 자료는 본문 근거에서 전부 제외하고 실제 API 저장과 컨테이너 실행을 기준으로 본실험을 새로 수행했다. 제품별 세 개의 독립 클러스터를 구성하고, privileged·권한 상승 허용·Linux capability 정책을 하나씩 격리하여 활성화했다. 각 제품·설치·정책군 조합을 다섯 번 반복하여 135개 실험 단위와 540개 실제 API 요청을 수집했다.

각 실험 단위는 정상 일반 Pod, 위반 일반 Pod, 정상 임시 컨테이너, 위반 임시 컨테이너의 네 사례로 구성했다. 허용 사례는 API 서버에서 Pod를 다시 조회해 저장 여부를 확인하고, 컨테이너 상태와 로그에서 실제 실행 및 Linux 프로세스 보안 상태를 확인했다. 일반 위반은 정책 고유 응답과 미저장을 함께 확인했다.

세 제품과 세 정책군의 모든 조합에서 일반 위반은 15/15 거부됐고 위반 임시 컨테이너는 15/15 허용·저장·실행됐다. privileged 사례는 전체 유효 capability와 `NoNewPrivs=0`, 권한 상승 사례는 `NoNewPrivs=0`, capability 사례는 `SYS_ADMIN` 비트가 확인됐다. 정상 사례는 모두 허용·저장·실행되어 관찰된 오탐은 없었다.

Gatekeeper는 ConstraintTemplate가 생성하는 ValidatingAdmissionPolicyBinding까지 확인한 뒤 반복을 시작해 준비 구간의 집행 경로 변화를 본집계에서 제거했다. 세 정책을 동시에 활성화할 때 생길 수 있는 정책 간 교란도 정책군별 격리로 제거했다.

별도 실제 대조 실험에서는 Pod Security Admission Baseline이 정상 임시 컨테이너를 허용·실행하면서 privileged 임시 컨테이너를 403으로 거부했고, 하위 API 권한이 없는 ServiceAccount의 요청은 RBAC가 403으로 거부했다. 두 거부 사례 모두 객체에 저장되지 않았다.

최신 원고는 연구 질문, 타겟 독자, 학술·실무적 기여, 오탐·미탐의 의미, 보안 영향, 도구별 원인, 완화책, 한계와 향후 연구를 새 실제 결과에 맞춰 다시 작성했다. 원자료, 자동 집계, 증거 해시는 `experiments/ephemeral-api-coverage/results/2026-09-19-live-matrix/`에 있다.
